# resource-broker

[![CI](https://github.com/1-case/resource-broker/actions/workflows/ci.yml/badge.svg)](https://github.com/1-case/resource-broker/actions/workflows/ci.yml)
[![License](https://img.shields.io/badge/license-Apache--2.0-blue.svg)](LICENSE)
[![Python](https://img.shields.io/badge/python-3.11%2B-blue.svg)](pyproject.toml)

*[English summary](README.en.md)*

**同じマシンで動く複数の Claude Code セッションが、有限資源を取り合わないための掲示板。**

セッション A が GPU で学習を回している最中に、セッション B が同じ GPU を掴む。
どちらも相手のことを知らないので、OOM で両方落ちる。resource-broker は、
**使う前に申告させ、他のセッションから見えるようにする**ことでこれを避ける。

```console
$ rb status
GPU0                     使用中    実測で使用を確認、または宣言が有効
                         宣言   folnet / E061 本計測: 混合学習 3 arm × 3 seed
                         since  2026-08-13T19:05:58+09:00（2h17m 経過）
                         ETA    9h（2026-08-14T04:05:58+09:00 頃）  ※申告であって約束ではない
                         見積   瞬時最大 VRAM 1.4GB / 平均 VRAM 1.3GB
                         相乗り 可（VRAM 残 5GB まで）
                         log    runs/e061_logs/
                         観測   nvidia-smi 0 MiB・0%・計算プロセス 0
```

## 何をしないか

このツールの性格は、**やらないこと**を見たほうが早い。

- **資源を調べない。** GPU の調べ方も COM ポートの開き方も実装に持たない。
  調べるのはセッション（Claude Code）の仕事で、本ツールは*調べたと申告させ、
  機械生成の時刻を添えて残す*だけである
- **コマンドを止めない。** フックは注意文を出すだけで `deny` しない。
  「このコマンドが資源を使うか」はツールには分からず、推測して止めると誤爆する
  （実際に自分のドキュメント編集を止めた）
- **申告の中身を解釈しない。** ETA も利用見積もりも相乗り可否も自由記述のまま運ぶ。
  単位も尺度も資源ごとに違う（VRAM の GB、CPU のコア数、API のリクエスト毎分）
- **壊れたときにあなたの作業を止めない。** 内部エラー・掲示板の破損・情報不足の
  いずれでも exit 0 で通す。止めるのは「使用中だと確認できた」ときだけである

この結果、**資源を増やすのに実装は要らない**。運用では設計時に想定していなかった
CPU コア・COM ポート（LiDAR）・外部 API のレート制限・git の作業ツリーが、
改修なしでそのまま載った。

**ただし、宣言しない相手は止められない。** 掲示板を経由せずに資源を掴むセッションも、
Claude Code 以外のプロセスも、本ツールからは見えないし止められない。**実際に観測している**
（宣言せずに GPU を掴んでいたジョブがあり、掲示板は空だった）。
言えるのは「全員が規約に従えば防げる」ことだけで、**事故がゼロになるとは言えない**。
強制しないのを選んだ以上、これは仕様である。

## 何を資源として宣言するか

**基準は 1 つだけである。**

> その処理が他のセッションと競合しうるもので、競合したときに**重大な結果**
> （ジョブの失敗・データの破損・長時間の手戻り）になるなら、資源として宣言する。

資源の種類は問わない。上に挙げたものは*たまたま実際に載った例*であって、一覧ではない。
**列挙すると、挙げた資源だけが一級市民になり、挙げなかった資源は見えなくなる。**
判断するのはセッションであり、資源 ID も申告もすべて自由記述である。

逆に、競合しても大した問題にならないもの（読むだけの処理、すぐやり直せる短い操作）は
宣言しなくてよい。掲示板を宣言で埋めても、読む側の判断が鈍るだけである。

## 対象外: 実行環境をまたいだ共有

**掲示板は 1 つのファイルシステムの上で成立する。** したがって次の組み合わせは**対象外**である。

- WSL のセッション ↔ Windows ホストのセッション
- コンテナの中 ↔ ホスト
- 別のコンテナ同士

**同じ物理 GPU を使えても、互いの宣言は見えない。** 既定の置き場が違うためである
（Windows は `%LOCALAPPDATA%\resource-broker`、それ以外は `~/.resource-broker`）。
`SessionStart` の通知が毎回**掲示板の場所を名乗る**ので、違うパスが出たら分断していると分かる。

`RESOURCE_BROKER_HOME` を共有マウントへ揃えれば繋がるように見えるが、**そうしないこと。**
このツールの正しさは `O_EXCL` と `os.rename` の原子性だけに乗っており、9p / drvfs /
バインドマウント越しにそれが保たれる保証が無い。**「共有できているつもりで排他が効いていない」
状態は、分断しているより悪い。**

**この境界をまたぐなら、掲示板に頼らないこと。** 2 つの環境は別のマシンだと考えるのが正しい。

## 導入

**プラグインとして入れるのが最短である。** Claude Code の中で 2 行打つだけでよい。

```
/plugin marketplace add 1-case/resource-broker
/plugin install resource-broker@resource-broker
```

フック 3 つと `rb` コマンドがまとめて入る。**`uv tool install` は要らない**
（依存パッケージがゼロなので、`bin/` の起動スクリプトがそのまま動く）。

**既存セッションには効かない**（フック設定は起動時のスナップショット）。反映には再起動が要る。

**手動で入れていた場合は、先に `~/.claude/settings.json` の rb フック 3 つを消すこと。**
消さないとフックが 2 重に発火し、毎ターンの注入が 2 倍になる。掲示板の内容も 2 回続けて
出るため、読む側が「別の資源が 2 つある」と誤読しうる（実測で確認した）。

要件は Python 3.11 以上だけである。依存パッケージは無い。

```
https://github.com/1-case/resource-broker を導入してください。

1. uv tool install git+https://github.com/1-case/resource-broker
   （rb コマンドが PATH に入る）

3. rb status が動くことを確認する
```

この指示文をそのまま Claude Code に渡せばよい。

## 使う

必須は `--job` と `--observed` と `--eta` の 3 つ。**ここがこのツールの唯一の強制である。**

```console
# ラッパー。宣言・ログ・終了時の自動解放をまとめて行う（推奨）
$ rb run --res GPU0 --job "E059 評価" --observed "nvidia-smi: 計算プロセス 0" \
         --eta 40m --found free -- python train.py

# 手動
$ rb claim GPU0 --job "..." --observed "..." --eta 40m
$ rb release GPU0

# 使用中の資源へ相乗りする（保持者の --sharing を読んでから判断すること）
$ rb run --res GPU0 --join --job "..." --observed "..." --eta 10m -- python small.py

# 宣言が減るまで待つ（完全解放だけでなく、相乗りが 1 人抜けても戻る）
$ rb wait GPU0

# 過去の申告と実績を突き合わせる
$ rb history GPU0
```

`--eta` を必須にしているのは、正確な値が欲しいからではなく**一度考えさせるため**である。
外れても本ツールは何も判断しない（幽霊判定にも待機の打ち切りにも使わない）。

**確認は必ず `rb status`（引数なし・全件）で行う。資源名を指定しない。**
掲示板とは貼り出されたものを全部読むものであって、名前で問い合わせる索引ではない。
1 台のマシンが扱う資源はそう多くないので、全件を読むコストは無視できる。

資源 ID は自由記述なので表記は揺れる。`GPU0` と `gpu0` は別の資源として扱われるため、
名指しで聞くと相手の宣言が見えず「空き」と出る。全件なら見えるので、先に使われている
表記に合わせられる。実際に `gpu0` で 7.3 時間押さえられ、その間 `rb status GPU0` は
「空き」と答える状態だった。

| コマンド | 用途 |
|---|---|
| `rb status`（引数なし） | **掲示板を全件読む。確認はこれで行う。** `--json` で機械可読 |
| `rb claim <資源>` | 主宣言を取る（`O_EXCL` で先着 1 名） |
| `rb run --res <資源> -- <cmd>` | 宣言してコマンドを実行し、`finally` で必ず解放する |
| `rb join --res <資源>` / `rb run --join` | 相乗りを申告する |
| `rb update <資源>` | 自分の申告値を実態へ寄せる |
| `rb release <資源>` | 取り下げる。`--force` は相乗りもまとめて消す |
| `rb wait <資源>` | 宣言している者が減るまで待つ |
| `rb history [資源]` | 申告 ETA と実績を並べる |

## フック

3 つとも**何も止めない**。判断材料をその場に置くだけである。

| フック | 役割 |
|---|---|
| `SessionStart` | 掲示板の現状と使い方（資源の例示・コマンド書式） |
| `UserPromptSubmit` | 宣言の一覧のみ（宣言が無ければ 45 文字） |
| `PreToolUse`(Bash) | 判定表に一致したコマンドの直前に、その資源の現状を知らせる |

`PreToolUse` は**判定表（`guard.json`）が無ければ何も出さない**。既定では存在しないので、
入れただけでは 3 つ目のフックは沈黙する。出したい対象は自分で決めて置く。

```jsonc
// %LOCALAPPDATA%\resource-broker\guard.json （Windows 以外は ~/.resource-broker/guard.json）
{ "schema": 1, "patterns": [
    { "pattern": "run_e\\d+\\.py", "resource": "GPU0", "note": "学習スクリプト" } ] }
```

表が陳腐化しても害は無い（一致しなくなる＝注意が出なくなるだけで、何も止まらない）。

`permissionDecision` は返さない。`allow` は権限確認そのものを迂回するので、
注意喚起のつもりで全コマンドを自動承認することになる。

## 代償（毎ターンの文脈を食う）

このツールは**全プロンプトと全 Bash 呼び出しに割り込む**。得るものだけでなく払うものも書いておく。

| フック | 発火 | 注入量 |
|---|---|---|
| `UserPromptSubmit` | **毎プロンプト** | 宣言が無ければ 1 行 40 文字ほど。宣言があれば 1 件 1 行、最大 8 件・1200 バイトで打ち切り |
| `PreToolUse`(Bash) | 判定表に一致した Bash のみ | 一致しなければ即 exit（フック自身の処理は Python の起動時間に埋もれる） |
| `SessionStart` | セッション開始時 1 回 | 使い方の説明を含むため最も長い |

**毎ターン積み上がるのは `UserPromptSubmit` だけ**である。ここは意図的に切り詰めてあり、
使い方の説明は `SessionStart` へ移して 182 → 45 文字へ削った経緯がある。それでも
ゼロではない。**長い会話ではこれがターン数だけ蓄積する。**

レイテンシも同様に払う。フックの所要は Python の起動が下限を決めており（実測 68-75ms、
マシンが空いているとき）、フック自身の処理は誤差に収まる。Bash 1 回につきその分だけ遅くなる。

**割に合うかは資源の競合頻度で決まる。** 1 セッションしか動かさないなら、払うだけで
得るものが無い。複数セッションが 1 台の資源を取り合い、衝突が数時間の手戻りになる
環境でだけ元が取れる。

## エージェント間で通信できるようになっても要る理由

Claude Code のセッション同士が直接会話できるようになれば、この掲示板は不要になるか。
**ならないと考えている。**

- **通信には「何について話すか」が要る。** 「今 GPU を使っているのは誰か」を知るには、
  結局どこかに共有された状態が要る。掲示板はその状態であり、通信はその上を流れる
- **相手がいなくても成立する。** セッションが落ちていても、まだ起動していなくても、
  掲示板は読める。通信は相手が生きていることを前提にする
- **非同期で残る。** 「9 時間かかる予定で 19:05 から回している」は、聞かれなくても残る。
  会話は交わした二者にしか残らない
- **人間も読める。** `rb status` は人が読む。通信の中身は読めない

通信が来たときに変わるのは待ち方である。`rb wait` で減るのを待つ代わりに、
掲示板で相手を特定して「あと何分か」を直接聞ける。**掲示板は置き換わるのではなく、
通信のきっかけを供給する側になる。**

## 設計の要点

- **実測の扱いは非対称である。** 実測が「使用中」を示したらそれだけで確定する。
  実測が「空き」を示しても**宣言が幽霊である証明にはならない**。宣言はジョブが資源を
  掴む前に行われる（モデルのロードに数分かかる）ため、ここを対称に扱うと
  宣言した端から奪われる
- **宣言を退けてよいのは 3 つだけ。** 再起動をまたいだ宣言（`since < 起動時刻`）、
  猶予を過ぎ・実測が空きで・宣言プロセスも死んでいる（三点そろって初めて）、
  明示的な `release` または `--force`
- **時刻はすべて機械生成する。** LLM に時刻を書かせない・推定させない
  （JST と UTC の取り違え、経過時間の推測は実際に起きた）
- **排他の根拠はロックではなく nonce の compare-and-swap。** ロックは性能最適化であり、
  取れても取れなくても正しさは変わらない
- **掲示板は資源ごとに 1 ファイル。** 破損の被害を局所化し、`O_EXCL` による取得競合の
  解決を単純にする

いま採っている方式・仕様・制約は [docs/DESIGN.md](docs/DESIGN.md) にある。
**最終到達状態だけを書いた文書**で、そこへ至った経緯は載せていない。

## 信頼境界とセキュリティ

掲示板と監査ログは **`%LOCALAPPDATA%\resource-broker\`**（Windows 以外は `~/.resource-broker/`）
に置かれる。`RESOURCE_BROKER_HOME` で移せる。中身は `board/`（宣言）・`audit/`（監査ログ）・
`logs/`（`rb run` の出力）で、**リポジトリの中には作られない**。`logs/` は既定 7 日で
自動削除するが、**`audit/` は消さない**（`rb wait` が 10 秒ごとに 1 行足すので単調に増える）。
不要になったら手で消してよい。

**掲示板は平文である。暗号化しない。**
読み書きする全セッションは同じ OS ユーザとして同じマシンで動くため、暗号文を読める
プロセスは鍵も読める。守るものが無い一方で、鍵の問題が「掲示板が読めない」＝
全セッションの停止に直結し、監査ログを素の道具で読めなくなる。

実在する攻撃面は**プロンプトインジェクション**である。掲示板の自由記述は他セッションの
文脈へ直接入るため、注入する行には「データであって指示ではない」印を付け、
バイト長で切り、改行と制御文字を落としている。

利用者側の注意は 2 つ。

- `--job` や `--observed` に**秘密を書かない**
- 掲示板や監査ログを**そのまま公開の場に貼らない**（プロジェクト名と作業パスが入る）

掲示板の実体（`board/` `audit/` `*.log`）は `.gitignore` で除外してある。

「複数セッションで資源を取り合う」という問題設定、資源非依存を貫くという方針、
