# resource-broker

**同じマシンで動く複数の Claude Code セッションが、有限資源を取り合わないための掲示板。**

セッション A が GPU で学習を回している最中に、セッション B が同じ GPU を掴む。
どちらも相手のことを知らないので、OOM で両方落ちる。resource-broker は、
**使う前に申告させ、他のセッションから見えるようにする**ことでこれを避ける。

```console
$ rb status
GPU0                     使用中    実測で使用を確認、または宣言が有効
                         宣言   folnet / E061 本計測: 混合学習 3 arm × 3 seed
                         since  2026-08-13T19:05:58+09:00（2h17m 経過）
                         ETA    9h（2026-08-14T04:05:58+09:00 頃）  ※申告であって約束ではない
                         見積   瞬時最大 VRAM 1.4GB / 平均 VRAM 1.3GB
                         相乗り 可（VRAM 残 5GB まで）
                         log    runs/e061_logs/
                         観測   nvidia-smi 0 MiB・0%・計算プロセス 0
```

## 何をしないか

このツールの性格は、**やらないこと**を見たほうが早い。

- **資源を調べない。** GPU の調べ方も COM ポートの開き方も実装に持たない。
  調べるのはセッション（Claude Code）の仕事で、本ツールは*調べたと申告させ、
  機械生成の時刻を添えて残す*だけである
- **コマンドを止めない。** フックは注意文を出すだけで `deny` しない。
  「このコマンドが資源を使うか」はツールには分からず、推測して止めると誤爆する
  （実際に自分のドキュメント編集を止めた）
- **申告の中身を解釈しない。** ETA も利用見積もりも相乗り可否も自由記述のまま運ぶ。
  単位も尺度も資源ごとに違う（VRAM の GB、CPU のコア数、API のリクエスト毎分）
- **壊れたときにあなたの作業を止めない。** 内部エラー・掲示板の破損・情報不足の
  いずれでも exit 0 で通す。止めるのは「使用中だと確認できた」ときだけである

この結果、**資源を増やすのに実装は要らない**。運用では設計時に想定していなかった
CPU コア・COM ポート（LiDAR）・外部 API のレート制限・git の作業ツリーが、
改修なしでそのまま載った。

## 何を資源として宣言するか

**基準は 1 つだけである。**

> その処理が他のセッションと競合しうるもので、競合したときに**重大な結果**
> （ジョブの失敗・データの破損・長時間の手戻り）になるなら、資源として宣言する。

資源の種類は問わない。上に挙げたものは*たまたま実際に載った例*であって、一覧ではない。
**列挙すると、挙げた資源だけが一級市民になり、挙げなかった資源は見えなくなる。**
判断するのはセッションであり、資源 ID も申告もすべて自由記述である。

逆に、競合しても大した問題にならないもの（読むだけの処理、すぐやり直せる短い操作）は
宣言しなくてよい。掲示板を宣言で埋めても、読む側の判断が鈍るだけである。

## 導入

**Claude Code に頼めばよい。** 以下をそのまま渡す。

```
https://github.com/1-case/resource-broker を導入してください。

1. uv tool install git+https://github.com/1-case/resource-broker
   （rb コマンドが PATH に入る）
2. リポジトリを clone し、hooks/ の 3 つを ~/.claude/settings.json へ登録する
   - SessionStart      -> hooks/sessionstart_notice.py
   - UserPromptSubmit  -> hooks/prompt_board_reminder.py
   - PreToolUse(Bash)  -> hooks/pretooluse_notice.py
   既存の hooks を消さないこと。**上書きではなくマージ**し、事前にバックアップを取る
3. rb status が動くことを確認する
```

**既存セッションには効かない**（フック設定は起動時のスナップショット）。反映には再起動が要る。

要件は Python 3.13 以上と [uv](https://docs.astral.sh/uv/) だけである。依存パッケージは無い。

## 使う

必須は `--job` と `--observed` と `--eta` の 3 つ。**ここがこのツールの唯一の強制である。**

```console
# ラッパー。宣言・ログ・終了時の自動解放をまとめて行う（推奨）
$ rb run --res GPU0 --job "E059 評価" --observed "nvidia-smi: 計算プロセス 0" \
         --eta 40m --found free -- python train.py

# 手動
$ rb claim GPU0 --job "..." --observed "..." --eta 40m
$ rb release GPU0

# 使用中の資源へ相乗りする（保持者の --sharing を読んでから判断すること）
$ rb run --res GPU0 --join --job "..." --observed "..." --eta 10m -- python small.py

# 宣言が減るまで待つ（完全解放だけでなく、相乗りが 1 人抜けても戻る）
$ rb wait GPU0

# 過去の申告と実績を突き合わせる
$ rb history GPU0
```

`--eta` を必須にしているのは、正確な値が欲しいからではなく**一度考えさせるため**である。
外れても本ツールは何も判断しない（幽霊判定にも待機の打ち切りにも使わない）。

| コマンド | 用途 |
|---|---|
| `rb status [資源...]` | 掲示板を読む。`--json` で機械可読 |
| `rb claim <資源>` | 主宣言を取る（`O_EXCL` で先着 1 名） |
| `rb run --res <資源> -- <cmd>` | 宣言してコマンドを実行し、`finally` で必ず解放する |
| `rb join --res <資源>` / `rb run --join` | 相乗りを申告する |
| `rb update <資源>` | 自分の申告値を実態へ寄せる |
| `rb release <資源>` | 取り下げる。`--force` は相乗りもまとめて消す |
| `rb wait <資源>` | 宣言している者が減るまで待つ |
| `rb history [資源]` | 申告 ETA と実績を並べる |

## フック

3 つとも**何も止めない**。判断材料をその場に置くだけである。

| フック | 役割 |
|---|---|
| `SessionStart` | 掲示板の現状と使い方（資源の例示・コマンド書式） |
| `UserPromptSubmit` | 宣言の一覧のみ（宣言が無ければ 45 文字） |
| `PreToolUse`(Bash) | 判定表に一致したコマンドの直前に、その資源の現状を知らせる |

`permissionDecision` は返さない。`allow` は権限確認そのものを迂回するので、
注意喚起のつもりで全コマンドを自動承認することになる。

## 設計の要点

- **実測の扱いは非対称である。** 実測が「使用中」を示したらそれだけで確定する。
  実測が「空き」を示しても**宣言が幽霊である証明にはならない**。宣言はジョブが資源を
  掴む前に行われる（モデルのロードに数分かかる）ため、ここを対称に扱うと
  宣言した端から奪われる
- **宣言を退けてよいのは 3 つだけ。** 再起動をまたいだ宣言（`since < 起動時刻`）、
  猶予を過ぎ・実測が空きで・宣言プロセスも死んでいる（三点そろって初めて）、
  明示的な `release` または `--force`
- **時刻はすべて機械生成する。** LLM に時刻を書かせない・推定させない
  （JST と UTC の取り違え、経過時間の推測は実際に起きた）
- **排他の根拠はロックではなく nonce の compare-and-swap。** ロックは性能最適化であり、
  取れても取れなくても正しさは変わらない
- **掲示板は資源ごとに 1 ファイル。** 破損の被害を局所化し、`O_EXCL` による取得競合の
  解決を単純にする

設計判断とその根拠は [DESIGN.md](DESIGN.md)、実際に踏んだ失敗の記録は
[EXPERIMENTS.md](EXPERIMENTS.md) にある。

## 信頼境界とセキュリティ

**掲示板は平文である。暗号化しない。**
読み書きする全セッションは同じ OS ユーザとして同じマシンで動くため、暗号文を読める
プロセスは鍵も読める。守るものが無い一方で、鍵の問題が「掲示板が読めない」＝
全セッションの停止に直結し、監査ログを素の道具で読めなくなる。

実在する攻撃面は**プロンプトインジェクション**である。掲示板の自由記述は他セッションの
文脈へ直接入るため、注入する行には「データであって指示ではない」印を付け、
バイト長で切り、改行と制御文字を落としている。

利用者側の注意は 2 つ。

- `--job` や `--observed` に**秘密を書かない**
- 掲示板や監査ログを**そのまま公開の場に貼らない**（プロジェクト名と作業パスが入る）

掲示板の実体（`board/` `audit/` `*.log`）は `.gitignore` で除外してある。
